# D2 用户关键问题（供 D4 写合约篇笔记用）

1. **MetaNodeStorage 感觉没用，直接被 External 继承掉了，最后绑定的也只有 Dealer？** 运行时确实不存在：abstract 不部署，继承被压平进 Dealer 一份字节码，abigen 也只绑 Dealer。价值在源码组织：① D5 的 External / Operation / View 三个兄弟需要共同基类来共享 `state`（各自声明会同名冲突，互相继承则依赖关系不对）；② 存储布局只有一个出处（代理升级纪律）；③ 公共 modifier（`onlyRegisteredPerp`、`onlyFundingRateKeeper`）和 `domainSeparator` 放这里所有兄弟都能用。只有一个子合约时合并进去完全等价。
2. **Dealer 感觉也没用，External 直接调的就是 Funding？** 区分"Dealer 角色"（链上唯一部署的地址，持有资金和 state，是 Perpetual 的 owner，核心）和 `MetaNodeDealer.sol` 文件（十来行的组装点）。External 是 abstract 不能部署，必须有具体合约来：合并 External/Operation/View、写构造函数、给部署脚本和 abigen 一个名字。只有 External 一个兄弟时两者合并等价。External 这层不能省：library 没有存储（state 要有人持有并传入）、modifier 只能挂在合约函数上、EIP-170 的 24KB 字节码上限（external 库函数单独部署，不占 Dealer 体积）。分层规律：Dealer 管组装，External 管入口和权限，library 管逻辑，越靠近部署越薄。
3. **这几个合约的调用顺序架构到底是什么样？** 链上只有 4 个地址：USDC、Dealer（state：保证金/持仓列表/风控参数/白名单）、Perpetual（paper/credit，owner=Dealer）、价格源；Storage/External 是 Dealer 源码的一部分，Funding/Position/Liquidation 是读写 Dealer state 的库。一笔 trade 四阶段同一交易内完成：① orderSender→Perpetual.trade ② Perpetual→Dealer.approveTrade(msg.sender, data)（Dealer 验 onlyRegisteredPerp + 白名单，返回谁/paper/credit 变化）③ Perpetual._settle 记账，0→非0 回调 openPosition，非0→0 回调 realizePnl 并清零 reducedCredit ④ Perpetual→Dealer.isAllSafe，Dealer 反过来调 Perpetual.balanceOf 和价格源 getMarkPrice 算净值；不安全则整笔回滚。回调里 Dealer 看到的 msg.sender 是 Perpetual（既用于鉴权，也是登记进 openPositions 的市场地址）。
4. **为什么这么划分文件？Perpetual / Dealer / Funding 各负责什么？** 依据是"数据归谁管"。Perpetual = 一个市场的持仓台账（paper/credit/fundingRate），复数，每个市场部署一个，不碰钱不判断安全；Dealer = 全局唯一的资金与风控中心（保证金、持仓列表、风控参数、白名单、真实 USDC），必须单数才能做全仓保证金（一笔保证金支撑多个市场、盈亏互抵）。分界线：按市场分开的数据放 Perpetual，跨市场共用的放 Dealer，所以算净值时两边要互相调用。Funding/Position/Liquidation 是 Dealer 的"科室"（library，不存数据，操作 Dealer 的 state）：存取款 / 开平仓登记 / 风控计算；拆库是为了按主题分文件、互相复用（取款和清算都用同一套安全检查）、绕开 24KB 上限。类比：交易所资金账户部门 vs 每个品种一本持仓台账。
5. **今天进度多少？/ 加快进度，测试你帮我写，我看懂就行。** 第 2 步起测试由 Claude 写（写完说明每个测试验什么 + 做变异验证），src 仍由用户手写。Perpetual 的回调测试用"测试合约自己实现 IDealer 当假 Dealer"的方式：`openCount` / `realized` 记录回调，变异（不清零 reducedCredit、每次都 openPosition）均能被抓到。
6. **ConstOracle 是做什么用的？** 价格永远不变的价格源（部署时写死，immutable）。Dealer 不存价格，每个市场在 `RiskParams.markPriceSource` 登记一个实现了 `getMarkPrice()` 的合约：ConstOracle（固定价）/ MockPriceSource（可改价，测试用）/ Pyth、Chainlink 适配器（生产）对 Dealer 完全等价，这就是 `IPriceSource` 接口的意义。实查参考项目：ConstOracle 只有定义、无任何引用，测试和 Sepolia 部署用的都是可改价的 TestMarkPriceSource；本项目的验收（价格下跌）、D5 部署、D8 端到端也都需要可改价，所以建议跳过不写。

## 用户踩过的坑（真实发生）
- （教学反馈）第 1 步只列字段名就让写，用户表示不知道这些变量是干什么的 → 改为先用 alice 开 1 BTC 的例子逐个讲 RiskParams / State 新字段再写。
- 第 1 步漏写常量 `Types.ONE = 1e18`（清单里三项只做了两项）；清算线注释写成"1300 >= 1000 触发清算"，实际安全条件是 `netValue >= maintenanceMargin`，相等算安全，严格小于才可清算。
- 第 2 步：`trade` 漏了结尾的 `require(isAllSafe(traderList))`（成交后不检查安全 = 可以无保证金开仓）；`openPosition` 回调写在更新 paper 之前（外部调用先于状态写入，违反 CEI，Dealer 回读 balanceOf 会看到旧值）；Perpetual 里多 import 了 `MetaNodeStorage`（Perpetual 不该依赖 Dealer 的存储）；`IDealer.sol` pragma 写成 `^0.8.10` 与其他文件不一致。
- 第 2 步：说"写完了"但没改 `Perpetual.t.sol`，3 个测试 `EvmError: Revert`（无数据）——owner 是测试合约，它没有 `approveTrade` 函数，调用不存在的函数就是无数据 revert。
- 第 2 步二次 review：`MetaNodeStorage` 的多余 import 仍未删；IDE 自动补了 5 个用不到的 forge-std import；假 Dealer 的 `isAllSafe` 有未使用参数 + 可收紧为 pure 两个编译警告（`forge build` 显示 "No files changed" 时看不到警告，要 `forge build --force`）；两个新测试（开仓只通知一次、平仓结算）没写就报"写完了"。
- 第 3 步 Position：逻辑全对（上限检查、push msg.sender、swap-and-pop + break），但没跑编译就提交：函数漏可见性 `internal`；`Types.State state` 参数和 `address[] addressList` 局部变量都漏数据位置 `storage`（引用类型必须写；这里必须是 storage 才能改到链上）；循环变量写成 `int256 i`（数组长度和下标是 uint256，int 与 uint 不能直接比较/索引）；pragma 又写成 `^0.8.10`（IDE 新建文件模板的默认值）。
- 把发给 Claude 的半句话打进了 `SignedDecimalMath.sol` 第 8 行（编辑器焦点没切走），整个项目编译失败；Claude 只删了那半句。`Liquidation.sol` 先搭函数壳的做法好，但 4 个命名返回值的函数里写了空 `return;` → Error 6777，命名返回值直接删掉 return 即可。
- ConstOracle 第一版把价格写在源码里（`return 30000e6`）且函数标 view：混淆了"部署后不可改"和"写死在源码"；改为 immutable + 构造函数传入。
- 第 4 步 Liquidation：`getTotalExposure` 和三个单人判断一次写对（符号、abs、按市场各自比例累加、`>=`、int/uint 转换都没错）。但 `_isAllMMSafe` 的 for 循环漏了 `++i` → 死循环，任何 trade 都会 OutOfGas；因为还没有调用方，16 个测试全绿也没暴露。`Funding._withdraw` 的 TODO 忘了替换。
